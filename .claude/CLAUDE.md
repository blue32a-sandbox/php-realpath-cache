# プロジェクト概要

PHPのrealpath cacheとOPcacheの挙動を検証するための実験環境を構築する。

特に、シンボリックリンクの切り替えが、PHPの実行結果に反映されるタイミングや条件を検証する。

WebサーバーやPHPの実行方式、キャッシュ設定による挙動の違いも比較できるようにする。

## 実行環境

Docker Composeを使用し、以下のSAPIで実行する環境を構築する。

* Apache + mod_php
* nginx + php-fpm

初期のPHPバージョンは8.5とする。

### 拡張性

今後、以下のような実行環境を追加する可能性がある。

* PHPバージョン
* SAPI

環境を追加する際に、既存の実験用プログラムや観測ツールをできるだけ変更せずに済む構成とする。

また、各環境は独立したキャッシュ状態を持ち、個別に検証できること。

## 検証用アプリケーション

サーバーサイドのアプリケーションでは、新しいバージョンのリリースをシンボリックリンクの切り替えで行う状況を再現します。そして、クライアントアプリケーションでは、その切り替わりを観測します。

### サーバーサイドアプリケーションの要件

* HTTPリクエストに対してJSON形式で結果を返す
* 結果には、切り替わりを確認するための情報や関連する設定値が含まれる
* シンボリックリンクの操作を行うことができる
* キャッシュを手動でクリアすることができる
* realpath cacheやopcacheの設定を変更して検証することができる

### クライアントアプリケーションの要件

* 定期的にサーバーサイドにHTTPリクエストする
* バージョンが切り替わるか、一定時間後に観測を修了させることができる
* 観測の様子を記録することができる

## 実装方針

* 実験のための最小限の構成とする
* 不要なフレームワークや依存ライブラリは導入しない
* Docker Composeで簡単に起動できるようにする
* 実験用PHPプログラムは各環境で共通化する
* 実行環境固有の設定は分離する
* 実験結果に影響する設定や条件を明示する
* 観測用エンドポイントおよびキャッシュ操作用エンドポイントは、ローカルの実験環境からのみ利用できるようにする
* Windows + Docker Desktop環境でも利用できる構成を考慮する

## 設計方針

検証対象は「SAPI × realpath cache × OPcache × シンボリックリンク」に限定し、それ以外の機能は追加しない。

* 切り替え方式: ドキュメントルート（`public/`）は実ディレクトリとし、`public/index.php -> ../private/vN/index.php` のファイル単位のシンボリックリンクを切り替える
* `private/vN/index.php` は共通処理（`lib/`）を include し、バージョンのみを持つ。`lib/` は切り替え・検証の対象外とする。v1 / v2 は事前に配置しておく
* シンボリックリンクの切り替えは `docker compose exec <svc> switch vN` で行う（中身は `ln -sfn` で、非アトミックであることを前提とする。Git Bash のパス変換を避けるためコンテナ内のスクリプトとする）
* キャッシュの状態参照は `public/_status.php`、キャッシュクリアは `public/_clear.php` の HTTP エンドポイントで行う。realpath cache はプロセスごと、OPcache はWebサーバーの共有メモリにあるため、CLI からはクリアできない
* レスポンスには PID を含め、ワーカーごとの違いを観測できるようにする。ワーカー数は `.env` の `WORKERS` で 1〜n を指定する
* キャッシュ設定は `.env` の値を PHP の ini に展開する。変更時はコンテナを再起動する
* 環境は Compose profiles で1つずつ起動する（複数環境の同時起動は想定しない）。公開ポートは `127.0.0.1` のみ
* 起動時にソースをコンテナ内の `/srv/app` へコピーし、`index.php -> v1` を作成する（Windows の bind mount で symlink を扱わないため）
* 観測クライアントは PHP CLI とし、記録は JSONL + 終了時のサマリーとする

## 進め方

* 作業は `TODO.md` のステップに沿って進め、完了した項目はチェックを更新する
* 各ステップの最後に確認項目を実行して結果を報告し、ユーザーの確認を得てから次のステップへ進む
* 設計判断が必要な場合は、選択肢をテキストで提示してユーザーの回答を待つ。未回答の事項を推奨案で勝手に決めない
* 構成は検証に必要な最小限に留め、推奨であっても機能を追加しすぎない
